# 时序数据分离

重复性、周期性的时序数据不写入 memory 系统，写入独立的数据通道。

## 核心原则

Memory 系统存储的是**有长期参考价值的知识和事件**，不是状态快照。时序数据的价值在于趋势分析，而非逐条记忆。

## 识别标准

以下类型的数据属于时序数据，不应使用 `workspace_memory_append`：

### 1. 周期性监控快照

```
❌ 不该写的：服务状态：正常运行 | CPU 12% | 内存 4.2GB | 无异常，交由 heartbeat 正常监控
```

特征：定期产生、内容高度重复、单条无独立价值。

### 2. 无状态变化的例行记录

```
❌ 不该写的：例行检查完成，所有服务正常，无异常事件
```

特征：格式固定、没有信息增量、仅证明"一切正常"。

### 3. 仪表盘式数据

```
❌ 不该写的：队列长度：42 | 在线用户：1,234 | 磁盘使用率：67%
```

特征：数值型、快速变化、脱离时间轴无意义。

## 处理方式

### 数据通道

监控数据写入 `workspace/data/snapshots/YYYY-MM-DD.jsonl`（JSON Lines 格式）：

```jsonl
{"timestamp":"2026-04-17T10:00:00Z","service":"api-gateway","cpu":12,"memory":67,"requests":1234,"errors":0}
{"timestamp":"2026-04-17T11:00:00Z","service":"api-gateway","cpu":15,"memory":72,"requests":1567,"errors":2}
```

### Daily Memory 中的状态变化事件

daily memory 中只记录**状态变化事件**，而非例行快照：

| 类型 | 示例 | 写入 memory |
|------|------|------------|
| 故障 | `API 网关 10:23 OOM，触发自动重启` | ✅ |
| 恢复 | `API 网关 10:31 恢复，根因是内存泄漏` | ✅ |
| 配置变更 | `数据库连接池从 20 调整为 50` | ✅ |
| 异常事件 | `支付接口超时率突然升到 5%` | ✅ |
| 结论性判断 | `确认是 Redis 缓存击穿导致，已加互斥锁` | ✅ |
| 例行正常 | `所有服务正常，无异常` | ❌ |
| 监控快照 | `CPU 12% | 内存 4.2GB | 请求 1234` | ❌ |

### Heartbeat Automation

Heartbeat automation 的监控输出直接写 `workspace/data/` 目录，不经过 memory 系统。

## 写入判断五问法

日常对话中决定是否写入记忆时，依次回答以下五个问题：

### 问题 1：未来需要？

> 这条信息未来 session 会需要吗？

- 不需要 → **不写**（如：临时调试命令、一次性查询结果）
- 需要 → 继续判断

### 问题 2：可实时获取？

> 能从代码、文档、配置文件中实时获取吗？

- 能 → **不写**（如：当前数据库 schema、API 端点列表）
- 不能 → 继续判断

### 问题 3：时序/监控？

> 是时序快照或监控数据吗？

- 是 → **写 data 目录**，不写 memory
- 不是 → 继续判断

### 问题 4：重复信息？

> 已存在于 MEMORY.md 或 topics 中吗？

- 是 → **不写**或更新已有条目的 `updated` 日期
- 不是 → 继续判断

### 问题 5：有明确标签？

> 能用 2-4 个标签归类吗？

- 有 → 附上 tags，**写入**
- 没有 → 重新考虑是否值得记忆，或使用通用标签
